# Spec 系統規格說明

本資料夾存放**系統現況規格**，描述系統「現在是怎麼做的」。

與 `requirements/` 的差別：需求文件寫的是**這次要改什麼**，上線後就凍結；規格文件寫的是**改完之後系統長什麼樣**，必須持續反映最新狀態。同一次異動會同時留下兩份紀錄——異動影響評估書記錄「差異」，規格文件記錄「結果」。

## 檔案架構

```
spec/
├── README.md              # 本檔案
├── frontend/              # 前端規格：畫面怎麼呈現、使用者怎麼操作
├── services/              # 後端規格：邏輯怎麼運算、資料怎麼流動
└── schema/                # 資料庫規格：資料怎麼存
```

## 命名規則

| 資料夾 | 命名格式 | 範例 |
| --- | --- | --- |
| `frontend/` | `{功能代號}_{畫面名稱}.md` | `F001_虛擬帳號查詢.md` |
| `services/` | `{功能代號}_{功能名稱}.md` | `F001_虛擬帳號查詢.md` |
| `schema/` | `{資料表名稱}.md` | `virtual_account.md` |

- `{功能代號}` 沿用 [library/index/functions/](../library/index/functions/) 的編號，同一功能的前端與後端規格用**相同代號**，才能互相對照
- `{資料表名稱}` 使用資料庫實際表名，維持半形小寫
- 單一功能規格過長時，可開同名資料夾拆檔（ex. `frontend/F001_虛擬帳號查詢/`）

## 撰寫範圍

三份規格最常見的問題是內容重疊或互相矛盾。以「這件事改了，誰該跟著改」為界線劃分：

| | frontend/ | services/ | schema/ |
| --- | --- | --- | --- |
| 主要內容 | 畫面結構、欄位與版面、前端驗證規則、互動與流程、呼叫哪些 API | 商業邏輯、運算規則、API 介面定義（request / response）、錯誤處理、下游系統呼叫 | 資料表欄位定義、型別與長度、索引、關聯、保留policy |
| 不該寫在這 | 商業邏輯（放 services） | 畫面長相（放 frontend）、欄位型別（放 schema） | 業務規則（放 services） |

### 共通要求

- 規格描述**現況**，不寫「本次調整為…」這類異動語氣——異動說明屬於異動影響評估書
- 前端規格提到 API 時，只寫「呼叫哪支」，介面細節以 services 規格為準，避免兩邊各寫一份而失同步
- 有畫面或流程圖時附上，圖片放同層 `assets/` 資料夾
