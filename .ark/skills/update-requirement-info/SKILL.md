# 變更現有需求基本資料

需求的基本資料散落在資料夾名稱、檔名、文件內容與需求總管等多處。手動修改極容易漏掉其中幾處，本技能負責**一次改齊，並找出既有的不一致**。

## 前置檢查

1. 讀 `.ark/config.yml`。不存在則告知使用者此專案尚未導入 ARK 並停止
2. 取得 `docs_root`
3. 讀 `{docs_root}/requirements/` 底下的說明文件，取得當前專案實際的命名規則
4. 讀需求總管 `{docs_root}/requirements/requirement_index.md`

## 步驟一：選擇需求

需求數量可能很多，**不要一次列出全部**。用互動式問答呈現：

1. 依「需求開立時間」由新到舊，列出**最近 10 筆**，每筆顯示：需求編號 / 需求名稱 / 狀態
2. 選項最後附一個輸入欄位，說明可輸入**需求編號或需求名稱**來查找不在清單中的需求

開立時間留白或需求總管沒有該欄位時，改以「年度 + 需求編號」由大到小排序。

### 查找規則

搜尋範圍為需求總管的**所有年度**，並一併比對 `{docs_root}/requirements/` 底下實際存在的資料夾——未登錄在總管中的孤兒資料夾也要找得到。

| 比對結果 | 反應 |
| --- | --- |
| 恰好一筆 | 顯示該筆摘要請使用者確認後採用 |
| 多筆（部分符合） | 列出符合的項目讓使用者選 |
| 零筆 | 依下方處理 |

### 找不到時

告知使用者已搜尋的範圍（需求總管所有年度 + 需求資料夾），並提供兩個方向讓使用者選擇：

| 選項 | 動作 |
| --- | --- |
| 可能輸入有誤 | 請使用者重新輸入；若記得部分關鍵字，可用部分名稱再查一次 |
| 這筆需求尚未開立 | 引導執行 `.ark/skills/new-requirement/SKILL.md` 開立新需求 |

不要自行猜測使用者想找哪一筆，也不要因為找不到就直接建立新需求——開立需求必須是使用者明確選擇的結果。

### 找到之後

若該需求**只有資料夾、需求總管沒有登錄**，或**只有總管列、資料夾不存在**，先告知使用者這個狀況，確認要如何處理後再往下——這本身就是一種不一致。

## 步驟二：先做一致性檢查（不要跳過）

**在異動之前先檢查**。若現況已經不一致，直接套用新值會把錯誤帶進去，事後更難分辨哪個才是對的。

逐項比對下表，列出所有不符：

| # | 檢查項目 | 比對對象 |
| --- | --- | --- |
| 1 | 資料夾名稱的三段（編號 / 單位 / 名稱） | 需求總管對應欄位 |
| 2 | 三份文件的檔名 | 資料夾名稱中的需求名稱 |
| 3 | 三份文件的標題（第一行 `#`） | 各自的檔名 |
| 4 | 需求書 §一 的需求編號、提出單位、PO、SA | 需求總管對應欄位 |
| 5 | 異動影響評估書表頭的需求編號、對應需求書 | 實際檔名與編號 |
| 6 | 需求總管中的兩個文件連結 | 實際存在的檔案路徑 |
| 7 | 資料夾所在的年度目錄 | 需求總管中該列所屬的年度區塊 |
| 8 | 需求資料夾 | 需求總管是否有對應列（孤兒資料夾） |
| 9 | 需求總管的每一列 | 是否有對應資料夾（幽靈列） |

發現不一致時：**列出來問使用者哪邊是正確的**，不要自行判斷。使用者確認後，把修正一併納入本次異動範圍。

沒有不一致就回報「檢查通過」，繼續下一步。

## 步驟三：互動式填單

顯示各欄位的**現值**，讓使用者選擇要變更哪些欄位（可複選），再逐一詢問新值。

| 欄位 | 備註 |
| --- | --- |
| 需求編號 | 常見情境是從留白補上正式編號 |
| 需求單位 | |
| 需求聯絡人 | |
| 需求聯絡人分機 | 選填 |
| 需求名稱 | 影響最廣，見下方警告 |
| 年度 | 變更會搬移資料夾 |
| PO | |
| SA | |

一次問一件事，不要一次丟出全部問題。

### 需求名稱與年度的警告

變更需求名稱會動到資料夾、三份檔名、三份標題與所有連結。若該需求在需求總管的狀態**已進入「開發中」之後**，還要提醒使用者：程式碼、branch 名稱、commit 訊息、`spec/` 文件裡可能也引用了舊名稱，那些超出本技能的範圍，需要另外處理。

## 步驟四：展開影響範圍

依下表展開本次要異動的所有位置。**每個欄位都要走完整張表**，不要只改想得到的地方。

### 需求編號

| 位置 | 內容 |
| --- | --- |
| 需求資料夾名稱 | `【需求編號】` 那一段 |
| 需求總管 | 需求編號欄 |
| 需求總管 | 兩個文件連結中的資料夾路徑 |
| 需求書 | §一 專案基本資料 → 需求編號 |
| 異動影響評估書 | 表頭 → 需求編號 |

### 需求單位

| 位置 | 內容 |
| --- | --- |
| 需求資料夾名稱 | `需求單位` 那一段 |
| 需求總管 | 需求單位欄 |
| 需求總管 | 兩個文件連結中的資料夾路徑 |
| 需求書 | §一 專案基本資料 → 提出單位 |

### 需求名稱

| 位置 | 內容 |
| --- | --- |
| 需求資料夾名稱 | `需求名稱` 那一段 |
| 三份文件檔名 | `需求書_X.md`、`異動影響評估書_X.md`、`測試問題追蹤表_X.md` |
| 三份文件標題 | 各檔第一行的 `#` 標題 |
| 需求總管 | 需求名稱欄 |
| 需求總管 | 兩個文件連結中的**資料夾路徑與檔名**（兩層都要改） |
| 需求書 | §一 專案基本資料 → 需求名稱 |
| 異動影響評估書 | 表頭 → 對應需求書 |

### 需求聯絡人 / 分機

| 位置 | 內容 |
| --- | --- |
| 需求書 | §一 專案基本資料 → 需求聯絡人（分機 / ） |

### 年度

| 位置 | 內容 |
| --- | --- |
| 需求資料夾位置 | 搬移至 `{docs_root}/requirements/{新年度}/`，目標年度資料夾不存在則先建立 |
| 需求總管 | 該列從舊年度區塊移到新年度區塊；新年度區塊不存在則比照既有格式新增 |
| 需求總管 | 兩個文件連結中的年度路徑 |

### PO / SA

| 位置 | 內容 |
| --- | --- |
| 需求總管 | PO 欄 / SA 欄 |
| 需求書 | §一 專案基本資料 → PO / SA |

異動影響評估書 §十一「確認紀錄」記的是**實際確認的人與日期**，屬於歷史紀錄，**不要**因為換了 PO / SA 就去改它。

## 步驟五：確認後執行

執行前，把「哪個檔案的哪一處、從什麼改成什麼」完整列給使用者確認。變更多時逐一列出，不要只說「已更新相關文件」。

執行時：

- 資料夾與檔名的更名，若專案有 git 版控，優先使用 `git mv` 以保留檔案歷史
- 需求總管的連結路徑若含空格，維持該檔案既有的跳脫寫法
- 只改上表列出的位置。文件正文中若有其他地方提到舊值（例如需求書內文敘述），**列出來問使用者**是否要一併更新，不要自動置換

## 完成後

1. 回報實際變更的每一處
2. 重跑步驟二的一致性檢查，確認全部通過
3. 若需求編號原為留白、本次補上，提醒使用者：後續的 branch、commit、對外文件若已使用暫用編號，需另外更正
