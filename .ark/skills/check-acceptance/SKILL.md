# 驗收標準檢核

開發完成到進入測試之間的閘門。目的是**在測試之前**確認實作真的達成了驗收標準，而不是等 SIT 才發現漏做。

## 前置檢查

1. 讀 `.ark/config.yml`，取得 `docs_root`
2. 選擇需求——依開立時間列出最近 10 筆，並附輸入欄位可輸入需求編號或名稱
3. 讀該需求的**需求書**與**異動影響評估書**
4. 讀測試問題追蹤表的「驗收檢核」區塊；沒有該區塊時，比照 `.ark/templates/測試問題追蹤表.md` 的格式新增

## 步驟一：產生檢核清單

清單只有兩個來源，**不要自行發明驗收項目**：

| 編號 | 來源 | 內容 |
| --- | --- | --- |
| `AC-xx`、`AC-Exx` | 需求書第五節（含 5.1 例外情境） | 業務面驗收條件 |
| `AC-Txx` | 異動影響評估書 | 技術面驗收條件 |

`AC-T` 從評估書這幾節萃取：

- 第四節 上游影響分析 → 既有呼叫方不受影響
- 第六節 資料庫異動 → 既有資料轉換正確
- 第七節 需求未定義事項的決策 → 決策內容確實被實作

清單已存在時**沿用既有列**，只補上新增的項目，不要重新產生一份覆蓋掉先前的檢核結果。

### 每條要填「驗證方式」

這欄是這份清單能不能被執行的關鍵。寫清楚**要做什麼才知道有沒有達標**：

- 執行哪個單元測試
- 用什麼資料、操作哪個畫面、看哪個結果
- 查哪張表的哪個欄位

寫不出驗證方式的項目要標示出來——那通常代表這條驗收條件本身不夠具體，應回頭找 PO 或 SA 釐清。

### 對應單元測試

單元測試依驗收標準撰寫，所以每條 `AC-` 原則上都該找得到對應的測試。找不到時列出來，這是**測試覆蓋的缺口**，不是清單填錯。

## 步驟二：逐條檢核

一條一條走，每條讓使用者選檢核結果：

| 結果 | 意義 |
| --- | --- |
| 通過 | 已確認達成 |
| 未通過 | 未達成，見下方處理 |
| 不適用 | 本次不涉及，**必須說明原因** |
| 未檢核 | 尚未確認，保持原狀 |

不要替使用者判定通過。**沒有實際驗證過的項目一律維持「未檢核」**，這份清單的價值完全建立在它誠實反映現況。

### 未通過的兩種處理

| 原因 | 處理 |
| --- | --- |
| 實作沒做到 | 回去改程式。記錄在備註，不要開測試問題——現在還沒進測試 |
| 規格或需求本身說不清楚 | **回報 SA**，不要自行解讀後實作 |

第二種要特別留意：這代表問題出在文件而不是程式。自行解讀後實作，程式與文件就從這裡開始分岔，而且不會有人發現。記錄下來，並提醒使用者切換到 Architect 處理。

## 步驟三：寫入

把檢核結果寫回測試問題追蹤表的「驗收檢核」區塊，填上檢核人與日期。

寫入前把整張清單的變更列給使用者確認。

## 完成後

1. 給出通過 / 未通過 / 未檢核 / 不適用的數量摘要
2. 列出所有**未通過**與**未檢核**的項目
3. 兩者都清空時才提示「可以進入測試階段」；還有未通過或未檢核就明說**尚不建議進測試**，並列出還差什麼
4. 有「因規格不清而未通過」的項目時，提醒切換到 Architect 釐清
5. 有找不到對應單元測試的 `AC-` 時，一併列出，提醒補測試
