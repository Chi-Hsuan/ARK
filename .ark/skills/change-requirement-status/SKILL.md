# 確認並變更需求狀態

每個階段結束時的關卡。做三件事：**檢查該階段的產出是否完整 → git commit → 更新狀態**。

狀態欄如果沒有人負責推進，`track-progress` 與 `sync-library` 的盤點就全部失準。這個技能就是那個負責的人。

## 前置檢查

1. 讀 `.ark/config.yml`，取得 `docs_root`
2. 選擇需求——依開立時間列出最近 10 筆，並附輸入欄位可輸入需求編號或名稱
3. 讀需求總管，取得該需求**目前的狀態**
4. 讀該需求總管的**狀態定義**章節——可用值以各專案的定義為準，不要自創

---

## 步驟一：判斷要執行哪個動作

依目前狀態決定，**不要讓使用者選一個與現況不符的轉換**：

| 目前狀態 | 動作 | 角色 | 變更為 |
| --- | --- | --- | --- |
| 需求探索 | 需求確認 | PO | 規格開立 |
| 規格開立 | 已完成規格書修改 | SA | 開發中 |
| 開發中 | 已完成程式 | PG | 測試中 |
| 測試中 | 已通過所有測試並上線 | SA | 已上線 |
| **測試中** | **需求確認**（因測試問題修需求書） | PO | **不改需求狀態**，見步驟四 |
| **測試中** | **已完成規格書修改**（因測試問題修評估書 / `spec/`） | SA | **不改需求狀態**，見步驟四 |

目前狀態與使用者想做的動作對不上時（例如狀態還在「需求探索」卻說程式寫完了），**停下來問**——可能是狀態沒跟上，也可能是選錯需求。

---

## 步驟二：檢查該階段的產出

逐項確認並列出結果。**未通過的項目要明確列出**，由使用者決定是先補齊還是照樣推進；使用者堅持推進時照做，但在回報中標明哪些未通過。

### 需求確認（需求探索 → 規格開立）

檢查需求書：

| # | 檢查項目 |
| --- | --- |
| 1 | 第一節專案基本資料：需求編號、提出單位、需求聯絡人、PO 已填 |
| 2 | 第二節需求源由 / 背景有內容 |
| 3 | 3.1 需求範圍說明有內容 |
| 4 | 3.2 需求項目至少一條，且每條都有編號 |
| 5 | 3.3 業務規則已填，或明確註明本次無業務規則 |
| 6 | 3.4 明確不在範圍內已填（留空等於默認全都要做） |
| 7 | 第四節非功能需求**無留空欄位**，不適用要寫「不適用」 |
| 8 | 第五節每條 `RQ-` 至少對應一條 `AC-` |
| 9 | 第六節名詞定義已整理 |
| 10 | **第七節待確認事項已清空** |

第 10 項最關鍵——待確認事項沒清空就進入評估階段，評估結論會建立在未定的前提上。

### 已完成規格書修改（規格開立 → 開發中）

| # | 檢查項目 |
| --- | --- |
| 1 | 異動影響評估書標 ★ 與 ★★ 的欄位都已填寫 |
| 2 | 第三節三項雙向檢查都已勾選 |
| 3 | 第五節列出的每個規格章節，`spec/` 對應文件都已修訂 |
| 4 | 第七節八個面向都有結論（含「不適用」） |
| 5 | 第十節確認紀錄已由 SA 簽署 |

### 已完成程式（開發中 → 測試中）

| # | 檢查項目 |
| --- | --- |
| 1 | 評估書第五節列出的異動都已實作 |
| 2 | 單元測試已撰寫且全數通過 |
| 3 | code review 的 🔴 必須修項目皆已處理 |
| 4 | 驗收檢核表無「未通過」與「未檢核」項目 |
| 5 | 掃描報告已存入 `release_docs/`（若已執行掃描） |

### 已通過所有測試並上線（測試中 → 已上線）

| # | 檢查項目 |
| --- | --- |
| 1 | 測試問題追蹤表**沒有未結案的問題** |
| 2 | 所有問題的文件更新狀態**沒有「待更新」** |
| 3 | 標為「不修正」的問題都有備註原因 |
| 4 | 驗收檢核表全部通過 |

## 步驟三：git commit

檢查通過後（或使用者確認照樣推進後）執行提交。

**先列出將被提交的檔案讓使用者確認**，再執行。使用者不同意提交時，跳過這步直接進行狀態更新，並在回報中註明未提交。

| 動作 | 提交範圍 | 訊息格式 |
| --- | --- | --- |
| 需求確認 | 該需求資料夾的文件變更 | `docs(req): {需求編號} 需求確認` |
| 已完成規格書修改 | 該需求資料夾 + `{docs_root}/spec/` | `docs(spec): {需求編號} 規格修訂完成` |
| 已完成程式 | 該需求資料夾的文件變更 | `docs(req): {需求編號} 開發完成` |
| 已通過所有測試並上線 | 該需求資料夾的文件變更 | `docs(req): {需求編號} 上線` |
| 測試階段修需求書 | 該需求資料夾的文件變更 | `docs(req): {需求編號} 需求書調整（{問題編號}）` |
| 測試階段修評估書 / 規格 | 該需求資料夾 + `{docs_root}/spec/` | `docs(spec): {需求編號} 規格調整（{問題編號}）` |

**程式碼的提交不由本技能代做**——那應該在開發過程中就分次提交，訊息也該描述實際改了什麼。發現有未提交的程式碼變更時提醒使用者自行處理。

不在 git 專案中時跳過這步，並告知使用者。

---

## 步驟四：更新狀態

### 一般情況

更新需求總管該列的狀態欄。

**「已通過所有測試並上線」還要多做一件事**：把「知識庫同步」欄從 `—` 改為 `待同步`。這欄不改，Librarian 的待同步盤點就看不到這筆需求，知識庫同步會直接被漏掉。

### 測試階段的文件修訂（例外）

需求狀態為「測試中」時，因某筆測試問題而回頭修文件——不論修的是需求書（PO）還是異動影響評估書與 `spec/`（SA）——**都不要動需求總管的狀態**。需求仍在測試中，沒有倒退回前一階段。

改為更新**測試問題追蹤表**：

1. 列出該需求**文件更新狀態為「待更新」**的問題供選擇。依角色預設篩選：
   - PO 進來：影響層面為「需求面」的問題
   - SA 進來：影響層面為「需求面」或「規格面」的問題
2. 確認本次改了哪幾份文件
3. 依下方規則更新該筆的**文件更新狀態**與**狀態**

#### 應更新文件有多份時

`應更新文件` 欄可能列了多份（判為需求面時是「需求書 → 異動影響評估書 → 系統規格」三份）。

**全部改完才能標「已更新」。** 只改了其中一份就標已更新，剩下的兩份會就此消失在流程中——這正是文件脫鉤最典型的路徑。

| 情況 | 文件更新狀態 | 狀態 |
| --- | --- | --- |
| 應更新文件全部完成 | `已更新` | 依實際情形：程式已配合修正 → `待驗證`；仍待改程式 → `修正中` |
| 只完成部分 | 維持 `待更新` | 維持 `修正中` |

只完成部分時，**在備註記錄已完成哪幾份**，讓下一個接手的人知道還差什麼。

#### 各自的檢查

| 角色 | 修訂前確認 |
| --- | --- |
| PO | 需求書的修改處與該筆問題描述對得上；第七節沒有因此新增未結的待確認事項 |
| SA | 異動影響評估書第五節有列出本次調整的規格章節；`spec/` 已依此修訂完成 |

#### 修完之後提醒

- **PO 修需求書後**：需求面的異動會往下游擴散，異動影響評估書與 `spec/` 通常也要跟著改，那屬於 Architect 的範圍。該筆問題在下游文件也改完之前，不要標「已更新」
- **SA 修評估書 / 規格後**：若該筆影響層面是「需求面」，先確認需求書是否已由 PO 修訂完成；上游還沒改就先標已更新，等於承認了一份還沒被確認的需求

## 完成後

1. 回報：檢查結果、提交的內容、狀態的前後變化
2. 有未通過仍推進的項目，**再列一次**，並說明後續要補
3. 提示下一棒是誰、可以做什麼

## 規則

- **只改需求總管的狀態欄與知識庫同步欄**，其他欄位不動
- 狀態值一律使用該專案狀態定義中的值
- 不要跳階段。使用者要一次從「需求探索」跳到「測試中」時，說明中間階段的產出不會有人檢查，確認後才照做
