# 撰寫異動影響評估書

異動影響評估書銜接需求書與系統規格書。它寫的是**差異**，不是現況——改完之後系統長什麼樣要寫進 `spec/`，兩邊各留一份紀錄。

## 前置檢查

1. 讀 `.ark/config.yml`，取得 `docs_root`
2. 選擇需求——依開立時間列出最近 10 筆，並附輸入欄位可輸入需求編號或名稱
3. 讀該需求的需求書
4. 確認異動影響評估書存在；不存在則從 `.ark/templates/異動影響評估書.md` 複製一份

### 需求書的把關

檢查需求書**第七節待確認事項**是否已清空。未清空時列出未結項目，並告知：這些問題會直接影響評估結論，建議先釐清。

使用者仍要繼續就繼續，但把未結項目複製到評估書第七節，**不要讓它們消失在流程中**。

---

## 步驟一：用索引找出異動範圍（不要憑需求書想像）

依序讀取，逐層收斂：

| # | 讀什麼 | 得到什麼 |
| --- | --- | --- |
| 1 | `{docs_root}/library/index/INDEX_README.md` | 各索引的欄位定義與查詢流程，**先讀這份再查** |
| 2 | `{docs_root}/library/system_overview.md` | 系統概要與主流程，先定位本次落在哪一塊 |
| 3 | `{docs_root}/library/index/api_index.md` | 依關鍵字與使用場景，找出候選 API 與 Service 入口 |
| 4 | `{docs_root}/library/index/functions/{API代號}.md` | 該 Service 呼叫的外部與共用 function |
| 5 | **反查**：以 function 或共用類別名稱搜尋 `functions/` 全部檔案 | 還有哪些 Service 也用了它——**共用影響** |
| 6 | `{docs_root}/library/index/downstream_api_index.md` | 涉及的下游系統與電文 |

第 5 步不要省略。改一支共用 function 時，直接影響只是其中一個 Service，**其他用到它的 Service 才是最容易漏掉的影響範圍**。

由上述整理出「**接下來要讀哪些規格文件**」的清單，**列給使用者確認後再讀**。使用者通常知道還有哪些沒被索引涵蓋。

索引是導航資料，不是規格也不是程式碼。`INDEX_README` 定義的可信順序是 **Source Code > Spec > INDEX**——索引與程式碼不一致時以程式碼為準，並提出索引更新建議。

### 索引查不到時

功能或 API 在索引中找不到，有兩種可能：**本次要新建**，或**知識庫缺漏**。這兩者的後果完全不同——當成新建但其實已存在，會寫出重複的規格。

**必須問使用者**，不要自行認定是新建。確認為知識庫缺漏的，記入第四節的「知識庫缺口」表。

---

## 步驟二：讀取規格

依上一步的清單，讀 `{docs_root}/spec/` 底下對應的文件。

`api_index.md` 的 `Spec` 欄已記錄路徑，**直接取用，不要自行拼路徑**。欄位填 `-` 時，後端規格的位置是：

```
spec/services/{API代號前綴}_{功能名稱}/系統規格書_{API代號}_....md
```

規格文件不存在時記入知識庫缺口，並在異動範圍總覽的「對應規格書路徑」欄填「新建」。

---

## 步驟三：逐節撰寫

**一節一節做，每節產出後讓使用者確認再往下**，不要一次生成整份文件——這份文件的價值在於逐節被想過，不在於被填滿。

建議順序：二 → 三 → 四 → 六 → 五 → 七 → 八 → 九 → 一。第一節的變更摘要留到最後寫，因為範圍確定後才摘要得準。

| 節 | 重點 |
| --- | --- |
| 二、異動範圍總覽 | 逐項列出 API CODE、功能名稱、異動類型。**破壞性變更**（回傳結構變更、必填參數新增、欄位語意改變、錯誤碼異動）標「是」者，第四節必須完成 |
| 三、需求 ↔ 異動對應表 ★ | 做完雙向檢查：每條需求都有對應異動（沒有的話是漏做還是不需異動？寫明），每項異動都有對應需求（沒有的話是否超出範圍？） |
| 四、上游影響分析 ★ | 誰在呼叫被異動的 API。先查 `api_index.md` 與 `system_overview.md`，但**索引未必記錄呼叫方**——沒有記載時一律填「待確認」並列入知識庫缺口，**不要推測** |
| 六、資料庫異動 | 特別確認既有資料是否需要轉換 |
| 五、規格書逐節異動指令 ★★ | 見下方 |
| 七、需求未定義、需決策事項 ★★ | 見下方 |
| 八、跨科協調 | 前置時間長，本文件完成時就該啟動，不要等規格書寫完 |
| 九、風險與注意事項 | |
| 十、確認紀錄 | **不要代填**。這是 SA 與 PO 實際確認的紀錄 |

### 第五節的紀律

這節是後續調整規格書的直接依據，寫法決定了規格書會被改成什麼樣：

- 每支 API 一個區塊，**只列需要異動的章節**
- 未列出的章節代表不動，後續調整規格書時不得修改
- 位置要明確指出，例如「於 1.5.2.4 之後插入」「修改 1.5.2.9 的檢核公式」，不要只寫「調整處理順序」
- 驗收條件來源要標註對應的需求書 `AC-` 編號

### 第七節的紀律

範本列的八個面向**逐項都要填，即使結論是「不適用」也要寫出來**。留空無法分辨是「不適用」還是「還沒想到」，而後者正是這節要抓的東西。

其中**下游失敗／逾時行為、權限控管範圍、部分成功的處理方式**這三項最常導致規格重寫，優先結案。

---

## 貫穿全程的紀律

**查不到就寫「待確認」。** 這份文件的價值建立在可信度上，一個看似合理的推測混進來，後面所有人都會當成已確認的事實。

**評估書寫差異，不寫現況。** 不要把整份規格搬進來。現況要查就去 `spec/`。

**產出一律標示為建議**，由使用者確認後才寫入。特別是第四、五、七節，那是 SA 的專業判斷，不是可以自動生成的內容。

**知識庫缺口要記下來。** 本次查不到的資訊，問到答案後應回補 `library/`，不要讓答案只留在這次討論裡。

---

## 完成後

1. 列出仍未完成的 ★ 與 ★★ 欄位，並提醒：這些未確認前不建議進入規格書撰寫階段
2. 列出知識庫缺口，提醒可切換到 Librarian 回補 `library/`
3. 提醒需求總管中該需求的狀態是否要更新為「規格開立」
4. 提示下一步：依第五節調整 `spec/` 規格文件
