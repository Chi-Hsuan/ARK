# 系統規格書修訂 / 撰寫

依異動影響評估書第五節的指令逐節修訂規格。這一步是「照著指令填空」，不是重新創作——判斷已經在評估階段做完了。

## 前置檢查

1. 讀 `.ark/config.yml`，取得 `docs_root`
2. 選擇需求——依開立時間列出最近 10 筆，並附輸入欄位可輸入需求編號或名稱
3. 讀該需求的異動影響評估書
4. 讀 `{docs_root}/spec/README.md`，取得該專案的命名規則與撰寫範圍

### 評估書的把關

第五節（規格書逐節異動指令）沒有內容時**停止**，告知使用者：規格修訂的依據來自這一節，沒有它就等於要在這裡重做評估。引導先執行 `.ark/skills/write-impact-assessment/SKILL.md`。

第三、四、七節仍有未確認的 ★ 項目時，列出來提醒——那些未定案的部分很可能讓這次修訂白做。使用者確認要繼續才往下。

---

## 步驟一：確認可還原（修改前必做）

規格是現況文件，改壞了很難靠記憶還原。動手前確認原始版本已進入 git 紀錄。

依序執行：

| 檢查 | 指令 |
| --- | --- |
| 是否在 git 專案中 | `git rev-parse --is-inside-work-tree` |
| 目標檔案是否已被追蹤 | `git ls-files --error-unmatch -- <檔案>` |
| 是否有未提交的變更 | `git status --porcelain -- <檔案>` |

處理方式：

| 狀況 | 反應 |
| --- | --- |
| 不是 git 專案 | 告知**改壞無法還原**，詢問是否仍要繼續。使用者堅持才繼續 |
| 檔案已追蹤且無未提交變更 | 通過，直接進行 |
| 檔案已追蹤但有未提交變更 | **停下來**。列出變更內容，請使用者先提交或還原 |
| 檔案未被追蹤 | 若是本次要新建的規格，正常，繼續；若是既有檔案從未提交，請使用者先提交 |

使用者同意時可代為執行提交，訊息用 `chore(spec): 規格修訂前存檔（{需求編號}）`。**未經同意不要自行 commit。**

這一步不要跳過，也不要因為「只改一小段」就省略。

---

## 步驟二：列出修訂清單

從異動影響評估書收集：

| 來源 | 得到 |
| --- | --- |
| 第二節 異動範圍總覽 | 每項異動對應的規格書路徑，或標記為「新建」 |
| 第五節 規格書逐節異動指令 | 每支 API 要動哪些章節、怎麼動 |
| 第六節 資料庫異動 | `spec/schema/` 要動的資料表 |

整理成「檔案 → 要動的章節」清單，**列給使用者確認後再動手**。

清單中若有評估書指定路徑但檔案不存在的情況，先確認是路徑寫錯還是應該新建，不要直接建一份新的。

---

## 步驟三：逐檔修訂

一次改一個檔案，改完讓使用者確認再進下一個。

### 只改指令列出的章節

評估書第五節**未列出的章節代表不動**。修訂過程中若發現其他章節也該改，**不要順手改**——列出來告訴使用者，由他決定是回頭補評估書，還是納入本次。

順手改的內容不會出現在評估書裡，等於繞過了評估與確認流程。

### 撰寫要求

| 要求 | 說明 |
| --- | --- |
| 只寫現況 | 不要寫「本次調整為…」「原本是…」。異動說明屬於評估書 |
| 不跨界 | 商業邏輯寫後端、欄位型別寫資料庫、畫面寫前端 |
| 前端只寫呼叫哪支 API | 介面細節以後端規格為準，不要兩邊各寫一份 |
| 位置照指令 | 評估書寫「於 1.5.2.4 之後插入」就插在那裡，不要自行重排章節順序 |

### 新建規格時

依 `{docs_root}/spec/README.md` 的命名規則命名，並**參考同資料夾既有規格的章節結構**，保持一致。同資料夾沒有既有檔案時，先問使用者要用什麼結構，不要自創。

---

## 步驟四：雙向檢查

改完後對照評估書第五節：

- 評估書列出的每一項異動，都有對應的規格修訂
- 本次修改的每一處，都能對應回評估書的某一項

任一邊對不上就列出來，讓使用者判斷是漏改還是多改。

---

## 完成後

1. 列出實際修改的檔案與章節，以及新建的檔案
2. 提醒使用者提交本次修訂（訊息可用 `docs(spec): {需求編號} {需求名稱}`）
3. 本次若**新增**了後端 API、service function 或下游呼叫，提醒：`library/index/` 的索引要等**上線後**由 Librarian 回寫，此時不要改 `library/`
4. 提醒需求總管中該需求的狀態是否要更新
