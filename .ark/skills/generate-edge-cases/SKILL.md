# 產生邊緣情境

正常流程通常想得到，出錯的路徑才是規格書錯誤處理的唯一依據，也是上線後最常出事的地方。本技能負責把這些情境提早攤開。

## 前置

讀 `.ark/config.yml` 取得 `docs_root`。由 `write-requirement` 呼叫進來時已經讀過，可略過。

讀取當前需求的需求書，重點是：需求項目（`RQ-`）、業務規則（`BR-`）、已寫好的驗收條件（`AC-`）、非功能需求。

一併讀 `{docs_root}/library/system_overview.md` 與 `{docs_root}/library/business/`，用來判斷哪些情境在這個系統真的會發生。

## 產出方式

逐類檢視，只提**與本需求真的相關**的情境。

| 類別 | 要問的問題 |
| --- | --- |
| 資料邊界 | 沒有資料、只有一筆、超過上限、欄位超長、特殊字元、全形半形 |
| 狀態邊界 | 目標資料已失效、已刪除、已被其他人改過、重複送出、同時操作 |
| 流程例外 | 下游逾時、下游回錯、部分成功部分失敗、中途中斷後重試 |
| 權限與角色 | 無權限、跨單位、權限剛好在本次異動被調整 |
| 時間 | 跨日、月底年底、日期區間顛倒、區間過長、時效剛好到期 |
| 相容性 | 既有資料不符合新規則、舊版本的資料或介面 |

### 每個情境要寫

| 欄位 | 說明 |
| --- | --- |
| 情境 | 什麼情況下會發生 |
| 為什麼重要 | 不處理會怎樣。寫不出後果的情境就不要列 |
| 建議預期結果 | 系統應如何反應 |
| 對應需求 | 相關的 `RQ-` 或 `BR-` 編號 |

## 三條紀律

**不要湊數。** 每一類都硬擠幾條，只會讓使用者失去耐心，真正重要的那幾條反而被淹沒。與本需求無關的類別直接說「本需求不涉及」。

**已涵蓋的不要重複列。** 先比對既有的 `AC-` 與 `AC-E`，已經寫過的情境不要再提一次。

**判斷不了的標為待確認，不要猜。** 例如「下游逾時要重試幾次」這種依系統慣例而定的問題，若知識庫查不到，列成待確認事項交給使用者，不要自行給一個看起來合理的數字——那會變成沒人確認過卻寫進文件的規格。

## 呈現與採納

分類列出建議，讓使用者**逐條選擇採納、修改或略過**。

採納的項目寫入需求書 5.1 例外情境驗收條件，編號沿用該表既有格式（例如 `AC-E01`）往下編。

標為待確認的項目，寫入需求書第七節待確認事項，不要寫進驗收條件——未確認的內容混在驗收條件裡，後續會被當成已定案的規格實作。

## 單獨執行時

使用者若不是從 `write-requirement` 進來，而是直接要求檢查有沒有漏想的情境，流程相同，但完成後提醒他：這些情境是否要一併補進需求書。
