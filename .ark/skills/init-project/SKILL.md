# 導入 / 升級 ARK

本技能處理三種情境，第一步先判斷是哪一種。

## 步驟一：判斷情境

讀取這兩個檔案：

- `.ark/VERSION` — 目前 `.ark/` 這份檔案是哪一版 ARK（隨 ARK 更新而變）
- `.ark/config.yml` 的 `ark_version` — 這個專案上次完成導入或升級時的版本

| 狀況 | 情境 | 前往 |
| --- | --- | --- |
| `config.yml` 不存在 | 導入 | 步驟二 |
| 兩者版本相同 | 檢查 | 步驟四 |
| `VERSION` > `config.yml` 的版本 | 升級 | 步驟五 |
| `VERSION` 不存在 | 安裝不完整 | 告知使用者 `.ark/` 檔案缺漏，需重新執行安裝指令，停止 |

`.ark/` 本身不存在時，代表這個 workspace 沒有 ARK 檔案，本技能無從執行——告知使用者需先執行 ARK 的安裝指令把檔案複製進來。

---

## 步驟二：導入

### 2.1 確認目標

顯示目前 workspace 的路徑，請使用者確認這就是要導入的專案。**不要往 workspace 之外寫檔案**；使用者若指的是別的資料夾，請他改開那個資料夾再執行。

### 2.2 決定專案名稱與文件根目錄

用互動式問答依序確認：

1. **專案名稱**——例如「分行數位服務」
2. **文件根目錄**——預設為 `docs_{專案名稱}`（例如 `docs_分行數位服務`），顯示預設值請使用者確認，允許改成其他名稱

命名提醒：

- 避免使用 `/`、`\`、`:` 等路徑不合法字元
- **避免空白**。資料夾名含空白會讓需求總管的 Markdown 連結必須寫 `%20` 跳脫，人工新增列時很容易寫錯

接著檢查該資料夾是否已存在：

| 狀況 | 反應 |
| --- | --- |
| 不存在 | 直接使用 |
| 存在但是空的 | 直接使用 |
| 存在且有內容 | 列出既有內容，詢問是要沿用（走步驟三的合併規則）還是改用其他名稱 |

### 2.3 產生設定檔

在 `.ark/config.yml` 寫入：

| 欄位 | 值 |
| --- | --- |
| `ark_version` | 與 `.ark/VERSION` 相同 |
| `project_name` | **2.2 使用者輸入的專案名稱原字串**，不加 `docs_` 前綴、不做任何加工 |
| `docs_root` | 2.2 決定的文件根目錄 |

以使用者輸入「分行數位服務」為例：

```yaml
ark_version: 1
project_name: "分行數位服務"
docs_root: "docs_分行數位服務"
```

使用者若把文件根目錄改成與預設不同的名稱（例如 `docs`），`project_name` 仍填使用者輸入的專案名稱，**不要從資料夾名反推**——兩個欄位各自獨立。

`config.yml` 已存在但 `docs_root` 指向不存在的路徑時（例如從別的專案複製過來的殘留設定），視為需要重新設定，詢問使用者後覆寫該欄位。

### 2.4 建立文件骨架

從 `.ark/templates/docs/` 複製整個結構到 `{docs_root}/`：

```
{docs_root}/
├── README.md
├── requirements/
│   ├── Requirements 需求資料夾說明.md
│   └── requirement_index.md
├── spec/
│   ├── README.md
│   ├── frontend/  services/  schema/
└── library/
    ├── system_overview.md
    ├── business/
    └── index/
```

複製後置換檔案中的 `{docs_root}` 佔位符為實際值。

**合併規則**：目標位置已有同名檔案時**一律保留既有檔案**，不覆寫，並把該檔列入最後的回報清單，讓使用者自行決定要不要比對範本。空資料夾用 `.gitkeep` 佔位，讓它們能進版控。

### 2.5 檢查轉接層

確認兩個工具的接入檔是否齊全。這些檔案由安裝指令複製，本技能只負責**檢查與回報**，不自行生成：

| 檔案 | 用途 | 缺少的後果 |
| --- | --- | --- |
| `.github/agents/*.agent.md` | Copilot 角色 | Copilot 叫不到 ARK 的角色 |
| `.github/skills/` | Copilot 技能 | Copilot 無法自動載入技能 |
| `AGENTS.md` | Codex 入口 | Codex 不知道這是 ARK 專案 |

缺少哪一個就明確說出哪個工具會不能用，並請使用者重新執行安裝指令。

### 2.6 回報

1. 列出實際建立的檔案與資料夾
2. 列出因為已存在而**跳過**的檔案
3. 提醒使用者：
   - 需 reload window，Copilot 才會載入新的 agent
   - `.ark/`、`.github/`、`AGENTS.md` 與文件骨架**都要提交進版控**，團隊其他人 clone 後才能直接使用
   - 可以接著用 Navigator 開立第一筆需求

## 步驟三：既有專案已有文件時的合併

導入既有專案時，`{docs_root}` 底下常常已經有文件。原則是**不動使用者的東西**：

- 既有檔案一律保留，只補上缺少的部分
- 既有的 `requirement_index.md` 保留原表格內容，不要替換成空範本
- 既有文件的命名規則若與 ARK 範本不同，**以既有的為準**，並提醒使用者 `Requirements 需求資料夾說明.md` 需要改寫成他們實際的規則——這份文件是所有技能讀取命名規則的來源，寫錯會讓後續每個技能都出錯

不要為了讓結構「符合範本」而搬動或改名既有文件。

---

## 步驟四：檢查

版本一致時執行完整性檢查，逐項確認並列出結果：

| # | 檢查項目 |
| --- | --- |
| 1 | `config.yml` 的 `docs_root` 指向的資料夾確實存在 |
| 2 | `{docs_root}` 底下 `requirements/`、`spec/`、`library/` 三個區塊齊全 |
| 3 | `requirements/` 有說明文件與需求總管 |
| 4 | `spec/` 有 README |
| 5 | 轉接層齊全（見 2.5） |
| 6 | `.ark/templates/` 底下三份文件範本齊全 |
| 7 | 技能轉接層齊全——執行 `.ark/tools/sync-adapters.sh`，缺漏時以 `--write` 補上 Copilot 那側，`AGENTS.md` 需手動補進正確的角色分組 |
| 8 | 需求總管的每一列都有對應的需求資料夾，反之亦然 |

有問題就說明缺什麼、會影響哪個功能、以及怎麼補。全部通過就回報「檢查通過」與目前的 ARK 版本。

---

## 步驟五：升級

### 5.1 說明差異

讀 `.ark/CHANGELOG.md`，把專案目前版本到 `.ark/VERSION` 之間的所有變更列給使用者，包含每一版需要執行的動作。

### 5.2 確認後執行

逐版執行 CHANGELOG 中列出的動作。**升級只做 CHANGELOG 明確要求的事**，不要順手「整理」既有文件。

升級動作若會修改既有文件，執行前先列出「哪個檔案的哪一處、從什麼改成什麼」讓使用者確認。

### 5.3 更新版本標記

全部完成後，把 `config.yml` 的 `ark_version` 更新為 `.ark/VERSION` 的值。

**中途失敗或使用者中止時不要更新版本標記**——版本號要誠實反映實際完成的狀態，否則下次升級會跳過未完成的步驟。

### 5.4 回報

列出實際執行的動作，以及使用者需要自行處理的部分（例如既有文件的格式調整）。
