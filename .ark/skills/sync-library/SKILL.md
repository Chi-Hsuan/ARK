# 知識庫同步

需求上線後把本次異動回寫 `library/`。這一步沒做，知識庫就開始失真——而失真通常不是因為有人拒絕同步，是因為沒有人記得。

## 前置檢查

1. 讀 `.ark/config.yml`，取得 `docs_root`
2. 讀需求總管 `{docs_root}/requirements/requirement_index.md`

---

## 步驟一：盤點

列出需要同步的需求：

| 類別 | 條件 |
| --- | --- |
| 待同步 | 狀態＝已上線，且知識庫同步＝待同步 |
| 漏填 | 狀態＝已上線，但知識庫同步欄留白 |

「漏填」要單獨標出來——它不是「不需同步」，是**沒有人判斷過**。

呈現格式：

```
📚 待同步盤點　·　待同步 3　·　漏填 1

- **RF20260030**　約定帳號查詢效能改善　·　SA 陳大同
- **RF20260028**　虛擬帳號批次匯入　·　SA 李小華
- ⚠️ **RF20260025**　交易明細匯出　·　同步欄留白，尚未判斷
```

使用者只是要盤點就到此為止，並提示可以選一筆開始同步。

---

## 步驟二：選擇需求並收集依據

從清單選一筆，讀取：

| 讀什麼 | 用途 |
| --- | --- |
| 異動影響評估書 | 本次異動了什麼，這是同步的起點 |
| `{docs_root}/spec/` 對應規格 | **實際上線的內容**，以此為準 |

### 以規格為準，不是以評估書為準

評估書寫的是**計畫**，開發與測試過程可能有落差。同步時以 `spec/` 的現況為準。

發現評估書與 `spec/` 對不上時，列出來告訴使用者——這代表其中一份沒有跟上，需要人判斷，不要自行選一邊。

---

## 步驟三：逐項比對要更新什麼

| 異動類型 | 要更新的檔案 |
| --- | --- |
| 新增功能或主流程異動 | `library/system_overview.md` |
| 新增或修改後端 API | `library/index/api_index.md` |
| 新增或修改 service 內的 function | `library/index/functions/{API代號}.md` |
| 新增或修改下游服務呼叫 | `library/index/downstream_api_index.md` |
| 業務規則變更 | `library/business/` |

整理成「要改哪些檔案、各改什麼」的清單，**列給使用者確認後再寫**。

---

## 步驟四：寫入

一次一個檔案，寫入前把變更內容列給使用者確認。

| 原則 | 說明 |
| --- | --- |
| 只寫現況 | 不要出現「本次新增…」「原本是…」。異動歷史屬於評估書 |
| 索引只放定位資訊 | 有什麼、在哪裡。細節留在 `spec/`，不要把規格內容搬進索引 |
| 沿用既有格式 | 比照該檔案既有列的欄位與寫法，不要自創格式 |
| 不刪既有內容 | 除非本次異動確實廢止了該項目，廢止要標註而非直接刪除 |

---

## 步驟五：更新需求總管

同步完成後，把「知識庫同步」欄填上 `已同步 / 姓名 / YYYY-MM-DD`。姓名要問使用者，不要自行填寫或留空。

### 判為「不需同步」時

確實有些異動不影響知識庫，例如純文案調整。這時填「不需同步」，但**必須在備註寫原因**。

沒有原因的「不需同步」與漏掉沒有分別——事後沒有人能判斷當初是想清楚了，還是跳過了。

---

## 完成後

1. 列出實際更新的檔案與內容
2. 回報需求總管的更新結果
3. 列出仍待同步的需求數量
4. 有「評估書與 spec 對不上」的落差時，單獨列出提醒處理
