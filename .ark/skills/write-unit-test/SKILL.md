# 單元測試撰寫

測試的判定依據來自**驗收標準與規格**，不是來自實作。

## 前置檢查

1. 讀 `.ark/config.yml`，取得 `docs_root`
2. 選擇需求——依開立時間列出最近 10 筆，並附輸入欄位可輸入需求編號或名稱
3. 讀需求書**第五節**（`AC-` 正常情境、`AC-E` 例外情境）與**第三節 3.3 業務規則**（`BR-`）
4. 讀異動影響評估書第二節，取得本次涉及的 API 與對應規格路徑
5. 讀 `{docs_root}/spec/` 對應規格，重點是處理順序、檢核規則、錯誤代碼表

---

## 步驟一：建立測試清單

清單來自四個來源，逐項展開：

| 來源 | 產生的測試 |
| --- | --- |
| 需求書 `AC-` | 每條至少一個測試 |
| 需求書 `AC-E` | 每條例外情境一個測試 |
| 需求書 `BR-` | 每條業務規則要涵蓋**符合**與**不符合**兩種走向 |
| 規格的錯誤代碼表 | 每個代碼都要有觸發它的測試 |

錯誤代碼那一項最常被略過——錯誤路徑寫不出測試，通常代表規格沒說清楚什麼情況會回這個代碼。這種情況列出來問，不要跳過。

清單列給使用者確認後再開始寫。

### 測試命名帶上編號

測試名稱或註解要帶上對應的 `AC-` / `AC-E` / `BR-` 編號，讓驗收檢核表的「對應單元測試」欄填得出來，也讓日後有人改壞測試時知道它在守護哪一條規格。

---

## 步驟二：撰寫

先看既有測試檔，比照現有的測試框架、命名慣例、mock 與測試資料的組織方式。**不要引入專案沒在用的測試風格或工具。**

### 判定條件的來源

實作程式可以參考——你需要知道怎麼呼叫、參數長什麼樣。但**斷言的內容一律來自 AC 與規格**。

具體來說：

| 該怎麼做 | 不該怎麼做 |
| --- | --- |
| 依 AC 寫出預期值，再看實作是否符合 | 執行實作，把跑出來的結果當成預期值 |
| 依規格的錯誤代碼表斷言回傳代碼 | 看程式丟出什麼代碼就斷言什麼 |
| 依業務規則寫邊界值 | 依實作的判斷式反推邊界 |

反推出來的測試只能證明程式跟自己一致，證明不了它符合需求——而後者才是測試存在的理由。

### 不要為了數字湊測試

沒有斷言、或斷言的是實作細節而非行為的測試，只會在重構時製造噪音。與其寫十個空洞的測試，不如把每條 AC 都確實覆蓋。

---

## 步驟三：執行

寫完跑一次測試，回報結果。

### 測試失敗時的預設立場

**先假設是程式不符合規格，不是測試寫錯。** 反過來假設，會讓人習慣性地改測試去配合實作，測試就失去意義了。

逐一判斷失敗原因：

| 原因 | 處理 |
| --- | --- |
| 實作沒做到規格寫的 | 回去改程式（`.ark/skills/write-code/SKILL.md`） |
| 規格與需求書矛盾，或規格沒寫清楚 | 回報 Architect 釐清，**不要自行決定哪個是對的** |
| 測試本身寫錯（斷言誤植、測試資料不對） | 改測試 |

第三種要**明確說出理由**再改。「改了就過了」不是理由。

---

## 完成後

1. 列出新增與修改的測試檔，以及各自對應的 `AC-` / `BR-` 編號
2. 做覆蓋檢查：需求書的每條 `AC-`、`AC-E`、`BR-`，以及規格錯誤代碼表的每個代碼，是否都有對應測試。缺的列出來
3. 把測試名稱回填到該需求測試問題追蹤表「驗收檢核」區塊的**對應單元測試**欄
4. 提示下一步：執行 `.ark/skills/check-acceptance/SKILL.md` 做驗收標準檢核
