# 撰寫 / 補完需求書

## 前置檢查

1. 讀 `.ark/config.yml`，取得 `docs_root`
2. 選擇需求——依開立時間列出最近 10 筆，並附輸入欄位可輸入需求編號或名稱。找不到時詢問是輸入有誤還是尚未開立，後者引導 `.ark/skills/new-requirement/SKILL.md`
3. 讀該需求的需求書。**先看目前填了什麼**，不要從零開始問已經寫好的內容
4. 讀 `.ark/templates/需求書.md` 確認章節結構（各專案的範本可能已調整）

## 選擇模式

用互動式選單提供四項，並可反覆執行：

| 模式 | 適用時機 |
| --- | --- |
| 引導填寫 | 不確定各段落該寫什麼 |
| 拆解需求項目 | 需求還很籠統，講不清楚要做什麼 |
| 產出預期結果初版 | 需求項目已定，要寫驗收條件 |
| Review | 填得差不多了，想找出矛盾與盲點 |

進入模式前先摘要目前需求書的完成度（哪幾節有內容、哪幾節空著），讓使用者知道自己在哪。

---

## 模式一：引導填寫

逐節說明，一次帶一節，不要一次倒出全部。每節都要講**該寫什麼、不該寫什麼、舉一個例子**。

| 章節 | 該寫 | 不該寫 |
| --- | --- | --- |
| 二、需求源由 / 背景 | 為什麼要做、不做會怎樣、目前的痛點 | 怎麼做、要開哪支 API |
| 3.1 需求範圍說明 | 整體要達成的事，一段話講完 | 逐條細節（那是 3.2） |
| 3.2 需求項目 | 一條一件事、可驗證、有編號 | 「優化」「改善」這類無法驗收的字眼 |
| 3.3 業務規則 | 檢核條件、限制、資格判斷，獨立編號 | 藏在敘述裡不編號 |
| 3.4 明確不在範圍內 | 這次刻意不做的事 | 留空——留空等於默認全都要做 |
| 四、非功能需求 | 資料量、回應時間、權限範圍、保存期限 | 留空。不適用要寫「不適用」 |
| 五、預期結果 / 驗收條件 | 前置條件 / 觸發情境 / 預期結果三段 | 「功能正常」這種無法判定的描述 |

舉例時**用使用者當前這個需求的內容舉例**，不要用不相干的範例——貼身的例子才看得懂。

填寫過程中若使用者提到系統無法確認的細節，不要替他決定，走下方「待確認事項」規則。

---

## 模式二：拆解需求項目

把籠統的敘述拆成可驗收的 `RQ-` 項目。

用提問引導，一次問一件：

1. 這件事**對誰**（哪種使用者、哪個單位）
2. 在**哪個畫面或介面**發生
3. **什麼條件**下才會發生
4. 系統要**做什麼**
5. 做完之後**看得到什麼變化**

拆解的判準：

- 一條需求只講一件事。出現「並且」「同時」通常代表該拆兩條
- 每條都要能回答「怎麼驗收」。答不出來就是還不夠具體
- 「檢核」「限制」「資格判斷」屬於**業務規則**，抽到 3.3 獨立編號，不要留在需求敘述裡

**編號規則：`RQ-` 與 `BR-` 一經建立就不再變動**——它們是異動影響評估書與規格書的追溯依據。新增用新號，不要重排既有編號；作廢的項目標註作廢，不要刪掉讓後面遞補。

---

## 模式三：產出預期結果初版

依 3.2 的每條需求項目產出驗收條件，填入第五節。

格式對應範本的三段欄位，這是為了讓後續轉成規格書的 EARS 句型（當【觸發情境】時，系統應【主要行為】）不需重寫：

| 欄位 | 內容 |
| --- | --- |
| 前置條件 | 使用者狀態或資料狀態 |
| 觸發情境 | 做了什麼動作 |
| 預期結果 | 系統應如何反應 |

要求：

- **每條 `RQ-` 至少對應一條 `AC-`**，並在「對應需求」欄填上
- 預期結果要能判定真假。出現「正確顯示」「運作正常」就是還不夠
- 涉及 3.3 業務規則的，驗收條件要涵蓋「符合」與「不符合」兩種走向

### 接著產生例外情境

正常流程的驗收條件產完後，**執行 `.ark/skills/generate-edge-cases/SKILL.md`**，依當前需求書的內容產出邊緣情境建議，填入 5.1 例外情境驗收條件。

### 最後逐條確認

產出的內容一律標示為**建議**，逐條讓使用者確認、修改或刪除。使用者未確認的項目不要寫入文件；已寫入但使用者存疑的，記入待確認事項。

## 模式四：Review

分三個層次檢查，結果分「矛盾 / 疑點 / 缺漏」三類呈現。

### 4.1 文件內部一致性

| 檢查 | 說明 |
| --- | --- |
| RQ ↔ AC 雙向覆蓋 | 每條需求都有驗收條件；每條驗收條件都對應得到需求 |
| BR 有無歸屬 | 每條業務規則都對應得到需求項目 |
| 3.2 與 3.4 是否打架 | 範圍內與明確不做的項目有沒有重疊 |
| 第四節非功能需求 | 有沒有留空的欄位（留空無法分辨是「不適用」還是「沒想到」） |
| 第七節待確認事項 | 是否已清空。未清空不建議進入異動影響評估階段 |

### 4.2 對照知識庫

讀 `{docs_root}/library/system_overview.md` 與 `{docs_root}/library/business/` 底下的文件，比對：

- 本需求描述的系統行為，是否與既有記載**矛盾**
- 本需求引用的業務規則，是否與既有規則**衝突**
- 本需求假設存在的功能或資料，知識庫中**是否確實存在**

發現矛盾時，明確指出「需求書說 X，但 `library/xxx.md` 說 Y」，**不要自行判斷哪邊是對的**——可能是需求寫錯，也可能是知識庫過期，這要由人決定。

知識庫查不到相關記載時說「查不到」，不要當作沒有衝突。

### 4.3 盲點提問

針對本需求提出疑點，目的是提前想清楚需求全貌。至少涵蓋：

- 沒說明的角色與權限範圍
- 沒定義的資料邊界（筆數、區間、上限）
- 既有資料的相容與轉換
- 與此需求相鄰、可能被波及但沒提到的功能
- 需求項目之間的先後順序或相依

每個疑點要說明**為什麼問**（不釐清會導致什麼），而不是只丟問題。

## 貫穿全程的兩條規則

### 特殊名詞 → 第六節

過程中出現業務名詞、系統代號、縮寫，一律登錄到第六節名詞定義。已收錄於 `{docs_root}/library/business/` 的，填連結而不是重抄一份定義。

### 待確認事項 → 第七節

任何「使用者答不出來」「需要問別人」「兩種做法未定」的問題，**當下就寫入第七節**，填上待確認問題、需誰確認、狀態。

不要放在對話裡就算了——對話會結束，文件不會。也不要替使用者猜答案填進正文。

---

## 完成後

1. 回報本次寫入了哪些章節
2. 列出仍空著的章節
3. 第七節若有未結案項目，列出來並提醒：定版前需清空
