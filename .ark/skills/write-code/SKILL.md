# 程式撰寫

依本次修訂過的系統規格實作。規格已經定義了要做成什麼樣，這一步是實作，**不是重新設計**。

## 前置檢查

1. 讀 `.ark/config.yml`，取得 `docs_root`
2. 選擇需求——依開立時間列出最近 10 筆，並附輸入欄位可輸入需求編號或名稱
3. 讀該需求的**異動影響評估書**與**需求書**（驗收標準）
4. 依評估書第二節「對應規格書路徑」，讀本次涉及的 `{docs_root}/spec/` 規格

### 規格的把關

規格文件尚未依評估書修訂完成時**停下來**——照著舊規格實作，等於白做。引導先執行 `.ark/skills/revise-spec/SKILL.md`。

判斷方式：比對評估書第五節列出的異動章節，與 `spec/` 對應章節的實際內容。

---

## 步驟一：決定要載入哪些套件規範

規範放在 `.ark/standards/{組}/`，一組一資料夾（例如 `cub/` 是資訊雲的 Java 套件）。

`.ark/standards/` 底下沒有任何規範時，告知使用者尚未建立套件規範，詢問是否在沒有規範的情況下繼續。

### 1.1 專案用哪幾組、哪幾份（讀 config）

讀 `.ark/config.yml` 的 `standards`：

```yaml
standards:
  cub: [cub-cloud-db, cub-cloud-redis]   # 只用其中幾份
  # cub: all                              # 整組都用
```

| 狀況 | 反應 |
| --- | --- |
| 已設定 | 取得候選清單，進入 1.2 |
| 未設定（`{}` 或缺少） | 列出 `.ark/standards/` 各組**實際存在**的文件讓使用者**複選**，選完寫回 config，再進入 1.2 |
| 設定中的文件不存在 | 告知缺少哪一份，詢問是要略過還是先補上 |

**這一步不要每次都問。** 專案用哪些規範是專案層級的決定，每次實作重問會得到不一致的答案。使用者主動說要調整時才重新詢問。

### 1.2 這次實作要讀哪幾份（依異動範圍收斂）

候選清單可能有七八份，但單次異動通常只碰到一兩個領域。依可用的資訊分三級判斷，**有高的用高的**：

| 級別 | 依據 |
| --- | --- |
| **A** | 規範文件的 frontmatter `packages`，比對專案的 `pom.xml` 等相依設定，確認實際有引入 |
| **B** | 檔名與 frontmatter 的 `keywords`，對照本次異動範圍（評估書與 `spec/` 已說明要動什麼），**提出建議清單由使用者確認** |
| **C** | 判斷不出來時，列出候選清單讓使用者複選 |

同一次執行中可以混用——有 frontmatter 的走 A，沒有的落到 B。這是刻意的設計，讓 frontmatter 可以漸進補上。

決定後告知使用者本次將依哪幾份規範實作，並讀取那些檔案。

### 1.3 發現 config 沒跟上時

若本次異動範圍明顯涉及某份規範，但它**不在 config 的清單裡**，提醒使用者：

> 這次會用到 `cub-cloud-oss`，但它不在專案設定裡。要加進 `standards` 嗎？

專案新引入套件卻沒人記得更新設定，是一定會發生的事。靠這個提醒讓 config 隨實際使用長齊，比要求人記得維護可靠。

## 步驟二：定位程式範圍

### 2.1 先確認程式碼在哪

依 `.ark/workflow.md` 的「程式碼的位置」判定：`.ark/config.yml` 的 `code_root`，未設定時預設 `{docs_root}/code/`。

該路徑不存在、是空的、或只有 `README.md` 與 `.gitignore`（也就是導入時沒有 clone 任何倉庫）時，**停在這裡問使用者程式碼在哪**，並說明你找過的路徑。得到答案且不是預設路徑時寫回 `code_root`。

程式碼還沒取得的話，請使用者先 clone 進 `{docs_root}/code/`，本次實作暫停——沒有既有程式碼就無從貼合風格，也無法判斷是新建還是修改。

### 2.2 從規格對應到實際檔案

1. 由評估書第二節取得本次涉及的 API CODE 與功能名稱
2. 由 `{docs_root}/library/index/api_index.md` 取得 Service 入口的完整類別路徑，再由 `{docs_root}/library/index/functions/{API代號}.md` 取得它呼叫的外部與共用 function
3. 在 2.1 確定的程式碼範圍內搜尋這些 API 與 function，定位實際檔案

整理成「要動哪些檔案」的清單，**列給使用者確認後再動手**。搜尋不到的項目列出來問，可能是命名不同，可能是本次要新建，也可能是那部分程式在另一個倉庫——後者要回到 2.1 補問位置，不要當成新建就直接寫。

### 建議先確認分支

實作前確認目前在哪個分支。在主要分支上直接改時提醒使用者是否要開新分支，分支名稱建議帶上需求編號，方便日後追溯。

## 步驟三：實作

一次做一個檔案或一項異動，做完讓使用者確認再繼續。

| 要求 | 說明 |
| --- | --- |
| 只做規格寫的 | 規格沒寫的功能不要自己加 |
| 遵守套件規範 | 步驟一載入的規範文件，特別是「禁止事項」與「常見錯誤」 |
| 貼合既有風格 | 命名、錯誤處理、日誌、註解密度都比照周邊既有程式碼，不要引入新的寫法 |
| 不順手重構 | 看到不相關的問題就記下來告訴使用者，不要一起改。混在同一次異動裡會讓 code review 無法分辨哪些是本次需求 |

### 發現規格有問題時

實作過程發現規格寫錯、寫漏、或與需求書矛盾，**停下來回報，不要自行解讀後實作**。

這屬於規格面問題，應由 Architect 判定並更新 `spec/`。自行解讀等於程式與文件從這裡開始分岔，而且不會有人發現——這是文件失真最常見的來源。

記錄下來並提醒使用者切換到 Architect 處理。

## 完成後

1. 列出實際修改與新增的檔案，以及各自對應規格的哪一節
2. 對照評估書第五節做雙向檢查：規格列出的異動都實作了；本次改動都對應得回規格
3. 提示下一步：
   - 依驗收標準撰寫單元測試
   - 執行 `.ark/skills/check-acceptance/SKILL.md` 做驗收標準檢核
4. 有「因規格不清而暫停」的項目時，列出來提醒先找 Architect 釐清
