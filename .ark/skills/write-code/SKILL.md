# 程式撰寫

依本次修訂過的系統規格實作。規格已經定義了要做成什麼樣，這一步是實作，**不是重新設計**。

## 前置檢查

1. 讀 `.ark/config.yml`，取得 `docs_root`
2. 選擇需求——依開立時間列出最近 10 筆，並附輸入欄位可輸入需求編號或名稱
3. 讀該需求的**異動影響評估書**與**需求書**（驗收標準）
4. 依評估書第二節「對應規格書路徑」，讀本次涉及的 `{docs_root}/spec/` 規格

### 規格的把關

規格文件尚未依評估書修訂完成時**停下來**——照著舊規格實作，等於白做。引導先執行 `.ark/skills/revise-spec/SKILL.md`。

判斷方式：比對評估書第五節列出的異動章節，與 `spec/` 對應章節的實際內容。

---

## 步驟一：確認套件規範

讀 `.ark/config.yml` 的 `standards`：

| 狀況 | 反應 |
| --- | --- |
| 已設定 | 讀取 `.ark/standards/{套件代號}/STANDARD.md`，告知使用者本次將依哪些規範實作 |
| 未設定 | 用互動式**複選**選單詢問，選項來自 `.ark/standards/README.md` 的可用規範表，選完寫回 `config.yml` |
| 已設定但對應的 `STANDARD.md` 不存在 | 告知缺少哪一份，詢問是要略過還是先補上 |

`.ark/standards/` 底下沒有任何規範時，告知使用者尚未建立套件規範，詢問是否要在沒有規範的情況下繼續。

**這一步不要每次都問**。設定寫在 config 裡是專案層級的決定，每次實作重問會得到不一致的答案。使用者主動說要調整時才重新詢問。

---

## 步驟二：定位程式範圍

從規格對應到實際程式碼：

1. 由評估書第二節取得本次涉及的 API CODE 與功能名稱
2. 由 `{docs_root}/library/index/functions/` 取得對應的 service 與 function
3. 在程式碼中搜尋這些 API 與 function，定位實際檔案

整理成「要動哪些檔案」的清單，**列給使用者確認後再動手**。搜尋不到的項目列出來問，可能是命名不同，也可能是本次要新建。

### 建議先確認分支

實作前確認目前在哪個分支。在主要分支上直接改時提醒使用者是否要開新分支，分支名稱建議帶上需求編號，方便日後追溯。

---

## 步驟三：實作

一次做一個檔案或一項異動，做完讓使用者確認再繼續。

| 要求 | 說明 |
| --- | --- |
| 只做規格寫的 | 規格沒寫的功能不要自己加 |
| 遵守套件規範 | 步驟一載入的 `STANDARD.md`，特別是「禁止事項」 |
| 貼合既有風格 | 命名、錯誤處理、日誌、註解密度都比照周邊既有程式碼，不要引入新的寫法 |
| 不順手重構 | 看到不相關的問題就記下來告訴使用者，不要一起改。混在同一次異動裡會讓 code review 無法分辨哪些是本次需求 |

### 發現規格有問題時

實作過程發現規格寫錯、寫漏、或與需求書矛盾，**停下來回報，不要自行解讀後實作**。

這屬於規格面問題，應由 Architect 判定並更新 `spec/`。自行解讀等於程式與文件從這裡開始分岔，而且不會有人發現——這是文件失真最常見的來源。

記錄下來並提醒使用者切換到 Architect 處理。

---

## 完成後

1. 列出實際修改與新增的檔案，以及各自對應規格的哪一節
2. 對照評估書第五節做雙向檢查：規格列出的異動都實作了；本次改動都對應得回規格
3. 提示下一步：
   - 依驗收標準撰寫單元測試
   - 執行 `.ark/skills/check-acceptance/SKILL.md` 做驗收標準檢核
4. 有「因規格不清而暫停」的項目時，列出來提醒先找 Architect 釐清
