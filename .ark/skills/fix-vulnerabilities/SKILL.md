# 弱點修復

依掃描報告逐項處理。**修復弱點常會改動原本的邏輯路徑**，所以完成後一定要重跑測試與驗收。

## 前置檢查

1. 讀 `.ark/config.yml`，取得 `docs_root` 與 `standards`
2. 選擇需求——依開立時間列出最近 10 筆，並附輸入欄位可輸入需求編號或名稱
3. 讀 `.ark/standards/` 底下該專案指定的 `STANDARD.md`

---

## 步驟一：取得掃描結果

用互動式選單詢問來源：

| 來源 | 動作 |
| --- | --- |
| 需求資料夾的報告 | 讀 `{docs_root}/requirements/{年度}/{需求資料夾}/release_docs/` 底下的報告檔 |
| 直接貼上 | 請使用者貼上報告內容或摘要 |
| 逐項口述 | 依下表逐欄詢問 |

每一項弱點需要的資訊：

| 欄位 | 說明 |
| --- | --- |
| 掃描工具 | Checkmarx / SonarQube |
| 規則或類別 | 例如 SQL Injection、Hardcoded Password |
| 嚴重度 | 依工具的分級 |
| 位置 | 檔案與行號 |
| 問題描述 | 工具給的說明 |
| 資料流 | Checkmarx 常會給 source → sink 路徑，有的話一併提供 |

資訊不足以定位程式時**要問清楚**，尤其是行號與資料流。位置不明就動手改，很容易改錯地方卻以為修好了。

報告若尚未存進 `release_docs/`，提醒使用者存放，那是上線文件的一部分。

---

## 步驟二：逐項判斷

一次處理一項，先判斷性質：

| 判斷 | 說明 | 處理 |
| --- | --- | --- |
| 真弱點 | 確實存在風險 | 進入步驟三修復 |
| 誤判 | 工具的規則誤觸，實際上已有防護 | 記錄理由，不改程式 |
| 源自規格 | 規格本身要求了有風險的行為（例如回傳含敏感欄位） | **回報 Architect**，不要自行改變規格定義的行為 |

### 判為誤判時

**必須寫下理由**：為什麼這裡實際上是安全的、防護在哪一段程式。

沒有理由的「誤判」與沒看沒有分別，而且下次掃描還會再出現一次，屆時沒有人記得上次為什麼放行。

第三種要特別留意——弱點的根因在規格時，改程式只會讓程式與規格不一致，問題還在。

---

## 步驟三：修復

| 原則 | 說明 |
| --- | --- |
| 用專案既有的元件 | 加解密、輸入驗證、編碼處理一律用專案既有的做法，不要自行實作 |
| 依套件規範 | `.ark/standards/` 的禁止事項優先於任何修法建議 |
| 最小改動 | 只改造成弱點的部分，不要順手重構 |
| 保持行為 | 修完的程式仍要符合規格。若不改變行為就無法修復，那是規格問題，回報 Architect |

### 不要只為了讓掃描過關

以下做法**一律不採用**：

- 加註解或設定去抑制規則
- 改變數名稱或寫法去規避規則比對
- 把檢查搬到掃描看不到的地方

這些會讓報告變乾淨，但風險原封不動，而且下一個人會以為這裡已經檢查過了。真的需要豁免時，走公司的例外申請流程，不要在程式裡動手腳。

---

## 步驟四：每修完一項都要確認三件事

弱點修復常改動輸入驗證與錯誤處理的路徑，**這三件事一件都不能省**：

### 1. 單元測試是否需要調整

不只是重跑既有測試，要判斷**測試本身需不需要改**：

| 情況 | 處理 |
| --- | --- |
| 修復新增了輸入驗證或錯誤路徑 | 補上對應的測試案例 |
| 既有測試失敗 | 依 `.ark/skills/write-unit-test/SKILL.md` 判斷是程式錯還是測試錯 |
| 既有測試因為修復而失去意義 | 說明原因後調整，不要直接刪 |

測試全過但沒有任何一條涵蓋這次修復的行為，代表這次修復沒有被守住——下次重構時會被改回去。

### 2. code review

執行 `.ark/skills/code-review/SKILL.md`，範圍是本次修復的改動。

### 3. 驗收標準檢核

執行 `.ark/skills/check-acceptance/SKILL.md`，確認修復沒有破壞原本已達標的項目。

---

**每修完一項就走一次這三步，不要累積到最後才一次做完。**

一次修五項再一起驗，測試失敗時無從判斷是哪一項造成的，只能逐一回退排查。逐項確認雖然慢，但每一步的因果都是清楚的。

跳過任何一項，等於用一個問題換另一個問題。

---

## 步驟五：記錄

在 `release_docs/` 產出或更新修復紀錄：

| 工具 | 規則 | 嚴重度 | 位置 | 判斷 | 處理方式 | 狀態 |
| --- | --- | --- | --- | --- | --- | --- |
| Checkmarx | SQL Injection | High | `XxxDao.java:88` | 真弱點 | 改用參數化查詢 | 已修復 |
| SonarQube | Hardcoded Password | Critical | `Config.java:12` | 誤判 | 為測試用假值，實際值由環境變數注入 | 誤判（已記錄理由） |

判為誤判的項目，理由要寫在這裡，下次掃描才有依據。

---

## 完成後

1. 列出各項的處理結果與統計
2. 列出**回報給 Architect** 的規格面項目
3. 提醒重新掃描，並把新報告存進 `release_docs/`
4. 逐項列出步驟四的三項確認結果（測試是否調整、review 是否通過、驗收是否維持）。有任何一項未完成就明確標出——尚未確認完之前不建議送測
