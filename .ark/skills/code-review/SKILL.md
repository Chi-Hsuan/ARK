# Code Review

檢視本次異動的程式碼。目標是在送審與掃描之前先攔下問題。

## 前置檢查

1. 讀 `.ark/config.yml`，取得 `docs_root` 與 `standards`
2. 選擇需求——依開立時間列出最近 10 筆，並附輸入欄位可輸入需求編號或名稱
3. 讀該需求的異動影響評估書第二節與對應的 `{docs_root}/spec/` 規格
4. 讀 `.ark/standards/` 底下該專案指定的 `STANDARD.md`

## 界定範圍

用 git 取得本次異動，不要review整個專案：

| 情境 | 指令 |
| --- | --- |
| 尚未提交 | `git status --porcelain` 與 `git diff` |
| 已提交在分支上 | `git diff <主要分支>...HEAD` |

範圍確認後列給使用者，包含檔案清單與大致行數。

範圍外的既有程式**原則上不 review**。例外是本次程式依賴到、且會直接影響本次正確性的部分——這種要標示為「既有問題」，與本次異動分開列。

## 檢查面向

### 一、規格符合度

- 規格寫的都做了，規格沒寫的沒有多做
- 處理順序、檢核規則、錯誤代碼與規格一致
- 錯誤代碼表列出的每個情況，程式都有對應路徑

與規格不符時要先分辨：是實作沒做到，還是規格本身有問題。後者回報 Architect，不要自行認定哪邊對。

### 二、品質

| 項目 | 看什麼 |
| --- | --- |
| 錯誤處理 | 例外有沒有被吞掉、失敗路徑有沒有處理、資源有沒有釋放 |
| 邊界 | 空值、空集合、上限、型別轉換失敗 |
| 重複 | 同樣的邏輯是否已存在於專案別處，能不能沿用 |
| 複雜度 | 過長的函式、過深的巢狀、難以命名的區塊 |
| 日誌 | 關鍵路徑有沒有足夠的軌跡；有沒有記錄到不該記的東西 |
| 併發 | 共用狀態、非執行緒安全的物件 |

### 三、格式與慣例

一律**比照周邊既有程式碼**：命名、排版、註解密度、檔案組織。

「與專案其他地方不一致」是有效的意見；「我覺得這樣比較好看」不是。沒有專案依據的個人偏好不要提。

### 四、安全性

先自查掃描工具最常抓到的類別，避免後面被退：

| 類別 | 檢查 |
| --- | --- |
| 注入 | SQL、指令、路徑，是否使用參數化或白名單 |
| 輸入驗證 | 外部輸入有沒有驗證長度、型別、範圍 |
| 敏感資料 | 帳號、身分證、卡號等是否被寫進日誌或回傳內容 |
| 機密硬編碼 | 密碼、金鑰、連線字串是否寫死在程式裡 |
| 權限 | 有沒有驗證呼叫者身分與資料歸屬，能不能查到別人的資料 |
| 例外訊息 | 回傳給前端的錯誤是否洩漏堆疊或內部結構 |
| 加解密 | 是否使用專案既有的元件，而不是自行實作 |

這一節是**送審前的自查**，不取代 SonarQube 與 Checkmarx。工具掃出的弱點屬於弱點修復流程。

### 五、套件規範

對照 `.ark/standards/` 的規範，特別是「**禁止事項**」與「常見錯誤」。這兩節通常是團隊實際踩過的坑。

## 輸出格式

依嚴重度分三級，各項標明位置：

| 層級 | 意義 |
| --- | --- |
| 🔴 必須修 | 正確性、安全性問題，或違反規範的禁止事項 |
| 🟡 建議修 | 品質問題，不修不會錯但會累積成技術債 |
| ⚪ 提醒 | 慣例不一致、命名可再清楚 |

每一項寫四件事：**位置（檔案:行號）、問題是什麼、為什麼是問題、建議怎麼改**。

只寫「這裡不好」而沒說為什麼，收到的人無從判斷要不要接受。

## 紀律

**沒問題就說沒問題。** 不要為了看起來認真而湊出意見，那會稀釋真正重要的那幾項。

**不要直接改。** 先完整報告，由使用者決定哪些要修。使用者要求後才動手，並逐項確認。

**區分本次與既有。** 既有程式的問題標示清楚，讓使用者能決定是否納入本次處理，而不是混在一起讓 review 範圍失控。

## 完成後

1. 給出各層級的數量摘要
2. 🔴 項目全部處理完之前，提醒尚不建議送審
3. 有規格面問題時，提醒切換到 Architect 釐清
4. 修改過程式後提醒：重跑單元測試，並執行 `.ark/skills/check-acceptance/SKILL.md`
