# 登錄測試問題

把測試發現的問題寫進該需求的測試問題追蹤表，並依影響層面決定哪些文件要跟著改、由誰負責。

## 前置檢查

1. 讀 `.ark/config.yml`。不存在則告知使用者此專案尚未導入 ARK 並停止
2. 取得 `docs_root`
3. 讀 `.ark/workflow.md` 的「影響層面判定」章節

## 步驟一：選擇需求

依「需求開立時間」由新到舊列出**最近 10 筆**（需求編號 / 需求名稱 / 狀態），並附一個輸入欄位讓使用者輸入需求編號或需求名稱查找。

找不到時告知已搜尋的範圍，詢問是輸入有誤還是該需求尚未開立；後者引導執行 `.ark/skills/new-requirement/SKILL.md`。**不要自行建立需求。**

選定後確認該需求資料夾底下有測試問題追蹤表。沒有的話，從 `.ark/templates/測試問題追蹤表.md` 複製一份再繼續。

## 步驟二：選擇測試環境

用互動式選單提供選項：

1. **SIT**、**UT**、**UAT**
2. **該表已存在的其他環境**——掃描追蹤表的 `##` 區塊，把不在上面清單中的一併列出（例如之前建過的 `UAT2`）

   > `## 欄位定義` 與 `## 驗收檢核` 是**保留區塊，不是測試環境**，掃描時要排除。環境區塊的特徵是底下有「編號 / 錯誤描述 / 影響層面…」那張表。
3. **自訂**——輸入欄位，讓使用者填新的環境名稱

選定的環境在表中沒有對應區塊時，比照既有區塊的格式新增一段（含表頭），位置接在最後一個環境區塊之後。

## 步驟三：問題描述

輸入框，請使用者描述測試發現的問題。

描述過於簡略時（例如只有「查詢有問題」），提醒使用者補上**在什麼情況下、做了什麼、預期什麼、實際什麼**——這段描述是之後判斷影響層面與重現問題的依據。提醒後仍堅持原描述就照填，不要擅自改寫使用者的文字。

## 步驟四：判定影響層面

用互動式選單提供三個選項，**每個選項下方附上說明**：

| 選項 | 說明 |
| --- | --- |
| 需求面 | 原始需求描述有誤或漏列，需求範圍本身要調整 |
| 規格面 | 需求正確，但異動評估或系統規格寫錯、寫漏 |
| 程式面 | 需求與規格皆正確，單純實作與規格不符 |

使用者不確定時，依問題描述給出建議並說明理由，但**最終仍由使用者選擇**。

判定為程式面時提醒一次：程式面代表文件完全不用改。若需求書或規格其實描述得不夠清楚，應該選規格面——判錯會直接造成文件與程式脫鉤。

## 步驟五：備註

輸入框，選填。可留白。

## 步驟六：自動帶出的欄位

以下三欄**依影響層面推導**，不要問使用者：

### 應更新文件

| 影響層面 | 應更新文件 |
| --- | --- |
| 需求面 | 需求書 → 異動影響評估書 → 系統規格 |
| 規格面 | 異動影響評估書 / 系統規格 |
| 程式面 | 無 |

需求面的異動會往下游擴散，三份都要列出，不能只寫需求書。

### 文件更新狀態

| 影響層面 | 文件更新狀態 |
| --- | --- |
| 需求面、規格面 | 待更新 |
| 程式面 | 不需更新 |

### 負責人

角色標註 **PO / SA / PG**，能對應到人名時在後面加括號，例如 `SA(李小華)`。

| 影響層面 | 主責角色 |
| --- | --- |
| 需求面 | PO（需求書），並列 SA（下游的評估書與規格） |
| 規格面 | SA |
| 程式面 | PG |

人名來源是**需求總管該列的 PO / SA 欄**。欄位留白就只寫角色代號，不要猜。PG 通常未登錄在需求總管，一般只寫 `PG`。

需求面同時涉及兩個角色時用 `/` 並列，例如 `PO(王小明) / SA(李小華)`。

## 步驟七：寫入

在該環境區塊的表格末端新增一列：

| 欄位 | 值 |
| --- | --- |
| 編號 | 沿用該區塊既有列的編號格式往下編；沒有既有列時用 `{環境}-01`（例如 `SIT-01`） |
| 錯誤描述 | 步驟三的輸入 |
| 影響層面 | 步驟四的選擇 |
| 應更新文件 | 步驟六推導 |
| 文件更新狀態 | 步驟六推導 |
| 狀態 | `待確認` |
| 負責人 | 步驟六推導 |
| 備註 | 步驟五的輸入 |

表格欄位順序**以該檔案實際的表頭為準**，不要照本文的順序硬填。表頭若與上表不符，依實際表頭對應，對不上的欄位留白並在回報時說明。

寫入前把整列內容列給使用者確認。

## 完成後

1. 回報寫入的位置與內容
2. 影響層面為**需求面或規格面**時，提醒使用者接下來要更新哪些文件，以及可以切換到哪個角色處理（需求書 → Navigator；異動影響評估書與規格 → Architect）
3. 需求總管中該需求的狀態若還不是「測試中」，提醒使用者是否要更新狀態
