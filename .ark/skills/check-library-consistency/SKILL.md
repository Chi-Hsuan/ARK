# 知識庫一致性檢查（library ↔ code）

確認 `library/` 是否真的反映程式現況。索引與實際對不上時比沒有索引更糟——因為人會相信它。

## 前置檢查

1. 讀 `.ark/config.yml`，取得 `docs_root`。不存在則告知使用者此專案尚未導入 ARK 並停止
2. 讀 `{docs_root}/library/index/INDEX_README.md`，取得各索引的定位、欄位定義與維護規則

以下提到的 `library/`、`spec/` 皆為 `{docs_root}` 底下的相對路徑。

## ⚠️ 執行前必須先告知成本

**這個檢查需要掃描程式碼，會消耗大量 token 與時間。**

第一件事就是把這句話講清楚，不要掃到一半才說。接著依下面的兩階段流程進行——**第一階段不掃程式**，很多問題在那裡就找得出來。

---

## 階段一：文件層檢查（不掃程式，先做這個）

只讀 `library/` 與 `spec/`，成本低：

| # | 檢查 |
| --- | --- |
| 1 | 索引各列的欄位是否齊全，有沒有整列留白 |
| 2 | `library/` 內的相對連結，指向的檔案是否存在 |
| 3 | `api_index.md` 的 `Spec` 欄路徑是否指向存在的檔案 |
| 4 | `api_index.md` 的每支 Service（`{API代號}`），`functions/` 底下是否有對應的 `{API代號}.md`，`spec/services/{API代號前綴}_{功能名稱}/` 底下是否有對應序號的系統規格書 |
| 5 | 需求總管中標記「已同步」的需求，其異動影響評估書列的項目是否確實出現在索引 |

先把這一階段的結果給使用者。**如果這裡就找出一批問題，建議先處理完再進第二階段**——文件層都對不齊時，掃程式只會得到更多雜訊。

---

## 階段二：程式比對（昂貴，需明確同意）

### 2.1 先確認比對基準

| 問題 | 為什麼要問 |
| --- | --- |
| 比對哪個分支或版本 | **預設應為已上線的版本**（主要分支或 release tag），不是開發分支 |
| 程式碼根目錄在哪 | 專案結構未必是單一 repo |

程式碼根目錄依 `.ark/workflow.md` 的「程式碼的位置」判定：`.ark/config.yml` 的 `code_root`，未設定時預設 `{docs_root}/code/`。該路徑找不到程式碼時問使用者，得到的答案若不是預設路徑就寫回 `code_root`。**沒問出位置就不要開始掃**——掃錯目標會把整份知識庫報成不一致。

這一步不能省。拿開發分支比對，會把「還沒上線的新功能」全部報成「知識庫缺漏」——但尚未上線的東西本來就不該出現在 `library/`。

### 2.2 估算範圍後再確認

先用低成本方式量規模（檔案數、大致行數），把數字告訴使用者，再讓他選範圍：

| 範圍 | 成本 |
| --- | --- |
| 單一 service | 低（建議從這裡開始） |
| 指定資料夾或模組 | 中 |
| 只檢查某一類（只比 API、只比下游呼叫） | 中 |
| 全專案 | 高，**需要再次確認** |

選定後告知預估的檢查批次數，並說明**可以隨時中止**。

### 2.3 分批進行

一批一個 service 或一個模組，每批結束就回報該批結果，不要全部跑完才輸出。

這樣使用者中途發現方向不對可以停下來，已完成的批次也不會白費。

### 2.4 比對項目

| # | 方向 | 檢查 |
| --- | --- | --- |
| 1 | 索引 → 程式 | `api_index.md` 列的 API，程式中有對應的實作入口 |
| 2 | 程式 → 索引 | 程式中對外的 API 入口，都出現在 `api_index.md` |
| 3 | 索引 → 程式 | `functions/{API代號}.md` 列的 function 確實存在，且確實被該 Service 呼叫 |
| 4 | 程式 → 索引 | Service 呼叫的**外部／共用** function，都出現在對應的 `functions/{API代號}.md`（依 INDEX_README 的收錄範圍，不含該類別自身的方法） |
| 5 | 索引 → 程式 | `downstream_api_index.md` 列的下游服務，程式中確實有呼叫 |
| 6 | 程式 → 索引 | 程式中呼叫的外部服務，都出現在 `downstream_api_index.md` |
| 7 | 文件 → 程式 | `system_overview.md` 提到的功能與主流程，程式中找得到入口 |
| 8 | 抽查 | `business/` 記載的業務規則，程式中有對應實作 |

第 8 項只做抽查，不要全面比對——業務規則與程式的對應往往不是一對一，全面比對的成本與誤判率都太高。

## 判讀差異：三種原因

同樣是「索引裡沒有這支 API」，處理方式完全不同：

| 原因 | 判斷方式 | 處理 |
| --- | --- | --- |
| 知識庫過期 | 該功能已上線一段時間 | 執行 `.ark/skills/sync-library/SKILL.md` 補上 |
| 已廢止未標註 | 索引有、程式沒有 | 確認是否廢止，廢止要標註而非直接刪除 |
| 尚未上線 | 對應的需求還沒上線 | **正常，不需處理** |

第三種特別容易誤判。發現差異時先回頭查需求總管，確認相關需求的上線狀態，再下結論。

## 「查無」不等於「不存在」

程式中找不到，可能只是：

- 命名與索引不同
- 動態註冊、設定檔驅動、註解式路由
- 分散在多個檔案或繼承自共用類別

所以一律回報為「**查無，請確認**」，不要斷言「程式中不存在」。斷言錯誤會導致使用者刪掉實際上還在用的索引項目。

---

## 輸出

每一項寫三件事：**哪裡不一致、可能原因、建議怎麼處理**。

依「需要處理 / 需要確認 / 正常（尚未上線）」分組，讓使用者一眼看出哪些真的要動。

## 紀律

- **不自動修改。** 完整報告後由使用者決定處理哪些，確認後才動手
- **全部通過就說通過**，不要為了顯得有做事而列出無關緊要的差異
- 只比對 `library/` 與程式的**對應關係**，不評論程式品質——那是 code review 的範圍

---

## 完成後

1. 給出各類別的數量摘要，以及實際掃描的範圍
2. 需要走同步流程的項目，提示執行 `sync-library`
3. 未檢查的範圍要明講，不要讓使用者以為全專案都檢查過了
