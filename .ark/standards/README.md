# 套件規範

公司內部套件的使用規範。實作程式時，`write-code` 技能會依 `.ark/config.yml` 的 `standards` 設定載入對應規範。

## 目錄結構

```
.ark/standards/
├── README.md                    # 本檔案，套件規範索引
└── {套件代號}/
    └── STANDARD.md              # 該套件的使用規範
```

## 可用規範

| 套件代號 | 套件名稱 | 適用情境 |
| --- | --- | --- |
| （尚未建立） | | |

新增套件規範時，在此表登錄一列，`write-code` 的互動選單會依這張表產生選項。

## 專案如何指定

`.ark/config.yml`：

```yaml
standards:
  - 套件代號A
  - 套件代號B
```

未設定時，`write-code` 會在第一次實作前用互動選單詢問，並把結果寫回 config。之後不再重複詢問；要調整時直接改 config，或請 Builder 重新設定。

## 撰寫規範時的格式

每份 `STANDARD.md` 建議包含：

| 段落 | 內容 |
| --- | --- |
| 適用範圍 | 什麼情況要用這個套件，什麼情況不要用 |
| 必須遵守 | 硬性規定，違反會被 code review 退回 |
| 慣用寫法 | 標準用法與範例程式碼 |
| 常見錯誤 | 實際踩過的坑，以及正確做法 |
| 禁止事項 | 明確不能做的事，附上原因 |

「常見錯誤」與「禁止事項」比「慣用寫法」更有價值——正確用法通常從既有程式碼看得出來，錯誤用法看不出來。

## 為什麼不放在 skills 底下

- 套件規範是**參照資料**不是任務。放進 `skills/` 會被工具依描述自動比對載入，在不需要的時候佔用 context
- 各專案用到的套件不同，`skills/` 的內容會被完整複製到每個專案
- 套件規範由公司統一維護，更新節奏與 ARK 的流程規則無關
