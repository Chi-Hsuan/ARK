# 套件規範

公司內部套件的使用規範。實作程式時，`write-code` 技能會依專案設定與本次異動範圍載入對應的規範。

## 目錄結構

**一組一資料夾**，組內一個套件一份文件：

```
.ark/standards/
├── README.md              # 本檔案
├── cub/                   # 資訊雲專案的 Java 套件（cub-cloud）
│   ├── cub-cloud-db.md
│   ├── cub-cloud-redis.md
│   ├── cub-cloud-security.md
│   └── ...
└── {其他組}/              # 未來若有 .NET 等其他技術棧，另開一組
```

分組的依據是**技術棧或套件家族**，不是專案。同一組規範可以被多個專案引用。

## 專案怎麼指定

`.ark/config.yml` 的 `standards` 是一個 map：

```yaml
standards:
  cub: [cub-cloud-db, cub-cloud-redis]   # 只用其中幾份
```

```yaml
standards:
  cub: all                                # 整組都用
```

```yaml
standards: {}                             # 尚未設定
```

未設定時，`write-code` 會在第一次實作前列出可選的規範讓使用者複選，選完寫回 config。之後不再詢問。

要調整時直接改 config，或請 Builder 重新設定。

## 三層決定

載入哪些規範是三層決定的結果，各自的變動頻率不同：

| 層級 | 記在哪 | 何時決定 |
| --- | --- | --- |
| 用哪幾**組** | `config.yml` 的 `standards` 鍵 | 導入專案時 |
| 用該組的哪幾**份** | `config.yml` 的清單值 | 第一次實作時問一次 |
| 這**次**讀哪幾份 | 不記錄 | 每次依異動範圍判斷 |

第三層的存在是為了避免每次實作都把整組規範讀進來。一個專案可能用了 8 份規範，但單次異動通常只碰到其中一兩個領域。

## 撰寫規範時的格式

每份規範建議包含：

| 段落 | 內容 |
| --- | --- |
| 適用範圍 | 什麼情況要用這個套件，什麼情況不要用 |
| 必須遵守 | 硬性規定，違反會被 code review 退回 |
| 慣用寫法 | 標準用法與範例程式碼 |
| 常見錯誤 | 實際踩過的坑，以及正確做法 |
| 禁止事項 | 明確不能做的事，附上原因 |

「常見錯誤」與「禁止事項」比「慣用寫法」更有價值——正確用法通常從既有程式碼看得出來，錯誤用法看不出來。

### frontmatter（選填，但建議新增文件時就帶上）

在文件開頭宣告這份規範管哪些套件：

```markdown
---
name: cub-cloud-db
packages: [cub-cloud-starter-db, cub-cloud-jdbc]
keywords: [資料庫, JDBC, DataSource, 交易, 連線池]
---
```

| 欄位 | 用途 |
| --- | --- |
| `packages` | 對應的 artifactId，讓技能能比對 `pom.xml` 精準判斷有沒有用到 |
| `keywords` | 判斷本次異動範圍是否相關 |

**這是選填的。** 沒有 frontmatter 的文件仍然可用，技能會退回用檔名與異動範圍判斷（見下方）。可以一份一份補，補一份就精準一份，不需要等全部補齊才切換。

**不要為了讓檔名對上套件名而改檔名**——用 `packages` 宣告即可，既有檔名維持原樣。

## 技能怎麼決定要讀哪幾份

`write-code` 依可用的資訊分三級，有高的用高的：

| 級別 | 依據 | 需要什麼 |
| --- | --- | --- |
| A | frontmatter 的 `packages` 比對專案的 `pom.xml` 等相依設定 | 該份文件有 frontmatter |
| B | 檔名與 `keywords` 對照本次異動範圍，提出建議由使用者確認 | 無 |
| C | 列出候選清單讓使用者複選 | 無 |

**混合狀態可以運作**——同一次執行中，有 frontmatter 的走 A、沒有的落到 B。這是刻意的：讓 frontmatter 可以漸進補上，不需要全體協調。
